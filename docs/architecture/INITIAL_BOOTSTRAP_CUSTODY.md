# Fixed initial custody, version 2

The existing platform-admin initial-bootstrap POST retains its five-field closed
request (`profile`, `service_id`, `idempotency_key`, `dry_run`, `reason`). It does
not accept commands, SQL, images, namespaces, credentials or receipt content.
The project-access, completed onboarding, exact active addon binding, owned
workload held at zero replicas (a fixed step instead requires a converged
rollout; see below), CNPG ownership/public CA, signature enforcement,
producer OCI/source/main CI matrix and cosign verification remain required.
The observed Service selector must match the exact Deployment selector.

`portal-sim-initial` has exactly four secret keys: `ca.crt`,
`CREA_SIM_MIGRATOR_DATABASE_URL`, `CREA_SIM_PORTAL_DATABASE_URL` and
`CREA_SIM_DATABASE_NAMESPACE`. The independent runtime URI must match the
actual held workload. Its raw binding may use only the supported unique
`sslmode=require|verify-full` and an optional exact fixed `sslrootcert`. This
is input compatibility, not TLS proof: the server-generated Job always uses
verify-full and the fixed mounted public CA, and 002 verifies the actual TLS
connections independently. Unknown modes, duplicate/extra query keys or another
CA are refused.
The fixed image runs:

1. Init `portal001`: `node packages/entrenamiento/src/migrar.ts`.
2. Main `initial`: `node packages/entrenamiento/src/preparar-custodia-reset.ts`.

The ordinary migrator owns the dedicated database; the runtime must be a
separate ordinary nonowner without superuser/BYPASSRLS, memberships in either
direction, DDL or TEMP. The 002 source verifies the two actual TLS connections,
PG18, matching native database identity, the retained 001 preparation and exact
catalog before returning its typed receipt. No runtime owner credentials enter
application configuration. The source-only fixture proves those commands and
checks; it is not a canonical gateway-image or hosted admission/readiness proof.

Three MAP profiles prepare the three training kernels: `map-sim-initial`
(kernel 01), `map02-sim-initial` and `map03-sim-initial`. They share one
definition. The profile name alone selects the kernel's service, database and
runtime role from a closed list, and the retained intent must carry exactly that
database and role. Every MAP-specific step below applies to all three alike.
Kernels 02 and 03 share kernel 01's Vault path under their own prefixed keys,
so each kernel's ExternalSecret may read only that kernel's properties from it.

Only the MAP profiles accept an earlier producer pin. crea-map re-pins its
image on every deploy, so a kernel's held image can trail crea-map's current
pin within hours. When the current pin names the image exactly once by another
digest, the server lists crea-map's `main` commits of the pin file, newest
first: at most 30, none older than 14 days. It reads the pin at each. The newest
revision that names the owned digest must name the image exactly once, with no
tag and no foreign `newName`, or the request is refused; no older revision is
tried. Any read failure refuses. Every registry, OCI, CI and signature check
that follows is unchanged. The `producer` proof reports `pin_match` (`current`
or `historical`), the matched commit as `pin_revision`, and that payload's
`pin_payload_sha256`. The retained identity keeps only the payload hash, so a
same-key collection after a further crea-map re-pin still matches its intent.
The portal profiles keep the exact current-pin rule.

The fixed MAP fresh guard, Prisma migration and compiled seed commands are
unchanged. Its five-key stdout remains `huella`, `codigoSha256`,
`fixtureSha256`, `roles`, `casos`: `roles=7` Member templates and `casos` the
seeded synthetic users, from the closed set {6, 52}: 6 for the lesson-only
seed (crea-map #960 and earlier) and 52 for the realistic online population
generated by crea-sim (crea-sim ADR-0005). Both are accepted while kernels
seeded by the older image remain; dropping 6 is a later cleanup. Any other
count is refused. The separate manifest has seven lessons; its lesson count is
not the seed stdout case count. The initial
portal/manifest wire works with the current initial MAP source. The separately
governed fresh reset-origin witness is required for reusable reset generations;
legacy initial metadata cannot be adopted as that witness.

## Fixed step `portal-sim-turno-vigente`

`portal-sim-turno-vigente` applies crea-sim's fixed portal step 003
(`sql/003-turno-vigente-por-persona.sql`) to the database that
`portal-sim-initial` prepared. It is a separate, closed profile, not a second
run of the initial one. It uses the same route and the same five-field
request. It keeps the same project, service, addon, binding, onboarding,
producer, signer, required checks, Vault path and four custody keys as
`portal-sim-initial`. Only the following differ.

- **Command.** One init container, `network-ready`, then
  `node packages/entrenamiento/src/preparar-turno-vigente.ts`, with no
  argument and no SQL. Neither the 001 migration nor the custody preparer runs.
- **Live workload.** The owned gateway may serve. Its rollout must have
  converged on its pinned image: the controller observed the current
  generation, and every Pod it counts belongs to the current template. The
  retained identity binds the Deployment UID and `deployment_generation`, not
  its resourceVersion, because status updates move a running Deployment's
  resourceVersion. A spec change between admission and collection is refused.
- **Ordering guard.** The image's own verified source revision must carry two
  files: `packages/entrenamiento/sql/003-turno-vigente-por-persona.sql`, whose
  SHA-256 is pinned in code, and `packages/entrenamiento/src/preparar-turno-vigente.ts`.
  That revision is the image's OCI revision, already bound to the signed main
  build. A missing or different file is refused before signature verification
  and before any Job exists. The Job runs the deployed image, so a gateway that
  does not yet accept the 003 catalog never meets it. Releasing a different
  step means a new step and a new pin; 003 itself is never edited.
- **Records.** Jobs, intents and receipts carry
  `enclii.dev/managed-by=isolated-fixed-step`, version `isolated-fixed-step-v1`
  and names `step-<24 hex>`. The initial history guard does not list them, so
  `portal-sim-initial`'s retained history stays readable with its own key.
  New identity and receipt fields are omitted when empty, so retained initial
  intents and receipts stay byte-for-byte canonical.

### Classification

The collector reads only the main container's stdout, with the same bounds and
closed-JSON rules as initial collection. It accredits exactly one shape as
`FIXED_STEP_APPLIED`:

- `fuente` = `portal-sim-turno-vigente`;
- `version` = `crea-sim-turno-vigente-v1`;
- `estado` = `APLICADO` or `YA_APLICADO`;
- `schemaSha256` and `databaseIdentitySha256`, each 64 lowercase hex.

Any other output from an accredited, exit-0 Pod is retained as
`FIXED_STEP_HELD` with `held_reason=output_unclassified` and only its stdout
hash. A failed Job is retained, on its own key, as `FIXED_STEP_HELD` with
`held_reason=job_failed`, from its native failed status alone; no log is read.
Integrity refusals (foreign Pod, image, command, exit code, restart or oversize
output) stay errors and write nothing. The database's immutable
`sim_capacitacion_custodia.turno_vigente_recibos` row remains the authority on
whether 003 is applied.

### Re-runs

A re-run is allowed, because the step is idempotent (`YA_APLICADO`). Each
operation key is its own operation: the Job name hashes
project/addon/service/profile and the key.

- **Same key.** A same-key POST never reruns. It reads or collects that one
  operation.
- **New key.** A new key is admitted only when every other fixed-step Job and
  every initial Job on the same addon/service has finished (Complete or Failed,
  with no active or terminating Pod) or is gone.
- **No wedge.** A retained receipt is not required to proceed. An operation
  whose Job expired uncollected (TTL one hour) no longer blocks, and its
  same-key POST returns held without writing.
- **Suspended Jobs.** A suspended Job blocks, as initial history does.

In the database, the step runs under the custody advisory lock in one
transaction, so even two concurrent keys cannot apply 003 twice. The gate
keeps one operation at a time so the history stays readable.

The GET status route accepts `step-<24 hex>` names. A live operation reads
`FIXED_STEP_EXECUTION`. A suspended or failed Job reads `FIXED_STEP_HELD`. A
succeeded Job not yet collected reads `FIXED_STEP_UNRETAINED`. A retained
receipt reads its own class.

## Fixed step `portal-sim-cierre-reconstruccion-paso`

`portal-sim-cierre-reconstruccion-paso` applies crea-sim's fixed portal step
004 (`sql/004-cierre-por-reconstruccion.sql`, crea-sim ADR-0007 §2c) on the
same portal database, after an accredited 003. It adds the close-by-rebuild
catalogue (the owner-only `cierres_reconstruccion` receipts, the gateway's
`sucesores_reconstruccion` link and the `cierre_reconstruccion_recibos`
witness). It **closes no reservation**: closing a reservation is the separate
`portal-sim-cierre-reconstruccion` profile, which does not exist yet (see the
[engineering backlog](../../ROADMAP.md#this-repository)).

It is step 003's profile in every respect (route, five-field request,
producer, signer, checks, live-workload rule, custody, records, re-run gate,
held receipts) except:

- **Command.** `network-ready`, then
  `node packages/entrenamiento/src/preparar-cierre-reconstruccion.ts`, with no
  argument and no SQL. crea-sim's preparer applies 004 only when the catalogue
  is exactly 003's, and answers `YA_APLICADO` when 004 is already there.
- **Ordering guard.** The image's verified revision must carry
  `packages/entrenamiento/sql/004-cierre-por-reconstruccion.sql`, with its
  SHA-256 pinned in code, and `packages/entrenamiento/src/preparar-cierre-reconstruccion.ts`.
- **Classification.** `FIXED_STEP_APPLIED` only for `fuente` =
  `portal-sim-cierre-reconstruccion-paso`, `version` =
  `crea-sim-cierre-reconstruccion-paso-v1`, `estado` `APLICADO` or
  `YA_APLICADO` and the two 64-hex hashes, reported as
  `native_receipt.cierre_reconstruccion_paso`. A step 003 line is never
  accepted as 004, nor the reverse; any other output is `FIXED_STEP_HELD`
  (`output_unclassified`). The database's own
  `sim_capacitacion_custodia.cierre_reconstruccion_recibos` row remains the
  authority on whether 004 is applied.

Both fixed steps share the manager label, so the re-run gate also keeps 003
and 004 from running side by side on the portal addon.

## Immutable history and uncertainty

The desired spec explicitly sets the public CA Secret volume's `defaultMode=0644`
and the two fixed `Exists/NoExecute` tolerations for `node.kubernetes.io/not-ready`
and `node.kubernetes.io/unreachable`, each for 300 seconds. These match the
[Kubernetes v1.36.4 core default](https://github.com/kubernetes/kubernetes/blob/v1.36.4/pkg/apis/core/v1/defaults.go)
and [DefaultTolerationSeconds admission source](https://github.com/kubernetes/kubernetes/blob/v1.36.4/plugin/pkg/admission/defaulttolerationseconds/admission.go),
corresponding to the pinned client/API version. They are explicit desired values;
other modes/tolerations or spec changes remain refused by strict matching.
This source compatibility proof does not establish the live server's version,
plugin configuration or admission result.

Admission is checked using server dry-run against actual Job/Pod policy before
any persisted Job. The server creates one suspended Job, verifies its returned
UID/spec/resourceVersion and then creates an immutable namespace-owned
`<job>-intent` ConfigMap. This binds the observed Job UID/creation version,
project/addon/service/binding/onboarding IDs, actual namespace/Deployment/Service/
CNPG UIDs, database/roles/public-CA hash, verified producer image/source/build/CI/
signature and hashes of the exact plan, Job spec, operation key and verified pin
payload. `pin_payload_sha256` is a payload hash, **not a Git pin revision**.
No unavailable Git revision is inferred. Credential values remain transient.

Only after that intent exists may fixed pull/Job credential custody and database
egress be prepared. Authority, namespace, registry custody, retained intent and
same suspended Job UID/spec are checked again. Activation uses its freshly read
resourceVersion in one PUT. The creation version is historical; normal Job
controller status changes do not rewrite it.

Each profile's first init container, `network-ready`, waits at most 120 s for
one TCP handshake with its own database host before any database step. The
Job's egress policy is created moments before activation, and a new Pod IP must
also reach the addon's ingress rules. Until the CNI programs both, connections
are refused at once, so a guard that tries once would hold the Job on a
transient (observed 2026-10-14 on `map-sim-initial`: `fresh-only` exited within
seconds with no server-side log). The probe uses the image's own `node`, does
not authenticate or read data, and prints only fixed messages, never the URL.
It changes the Job spec hash, so it applies to new operations only; it does not
resume or adopt held history.

The Job name is deterministic for project/addon/service/profile and excludes the
request key. Each MAP kernel therefore has its own Job name, and kernel 01's
name is unchanged. Its namespace Create is the atomic arbiter: concurrent
requests with the same or different keys can persist/activate only one Job. The
operation-key SHA remains in the immutable intent; a later incompatible-key
POST is refused.
The history list remains a refusal guard for old keyed Job/intent names, which
cannot be adopted into this new name. No database or extra launch lock is added.

A timed-out create/PUT does not retry, repair, adopt or create a new operation.
The implementation reads the same ID after an unknown create outcome and
returns held. A later POST cannot resume a suspended/failed Job, a missing
intent or an intent whose Job/receipt is missing. Another operation key is
refused while initial history for the same addon/service exists. No third
launch record or reset adapter is introduced. These rules bind initial
profiles; the fixed step above has its own per-key re-run rule.

After a complete Job, the explicit same-key POST may collect once. The server
requires the exact retained Job UID/spec, one controller-owned successful Pod,
fixed init/main source image/digest and zero exit/restarts for every container.
It reads only fixed container stdout with an 8192-byte UTF-8 cap and one closed
JSON object, rejecting duplicate/unknown/missing keys, malformed values and
already-prepared output. Portal001/002 must report fresh `PREPARADO`; MAP keeps
its fixed seed schema. No raw logs are returned. Job, Pod, intent and authority
are re-read before writing the immutable `<job>-receipt` ConfigMap. A conflict
or unknown receipt-write result returns held and performs only a same-ID read.

Both ConfigMaps belong to the namespace UID rather than the TTL Job. Their
closed payload/hash/labels/ownership are validated; they cannot be repaired or
updated. The existing GET is read-only, including after Job TTL deletion. It
never collects logs or creates a ConfigMap. Suspended/failed history is labelled
`INITIAL_ONLY_HELD`; completed execution awaiting explicit retention is
`INITIAL_ONLY_UNRETAINED`. A retained typed receipt is `INITIAL_ONLY`.

These records do not assert current Ready, a native reset origin, exclusion,
release ACK, a live SSO exercise, mail delivery or reusable custody. Actual
Enclii source/admission, human secret-policy readback and hosted UID/CA/ordinary
role checks remain independent gates before any live initial bootstrap.

## Witnessed close after reconstruction

The separate `portal-sim-cierre-reconstruccion` fixed profile consumes an
immutable pre-cut origin/fence observation, successor binding and native initial
seed receipt, and applied004 evidence. Its caller supplies only closed IDs and
the retained read reference. See the [complete contract](PORTAL_RECONSTRUCTION_CLOSE.md).
Legacy initial and observation records remain historical; missing origin
authority is never backfilled or inferred from the current addon.
